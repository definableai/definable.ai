`definable.memory` stores session-scoped conversation history and makes it available to future runs. It is designed to preserve continuity without forcing every application to build its own persistence and summarization layer.

## What memory is for

Use memory when the system should remember prior exchanges, summaries, or recallable conversation state across runs for the same session.

Memory is not the same as knowledge:

- memory preserves what happened in prior conversations
- knowledge retrieves from an external document corpus

## Public API

| Type | Purpose |
| --- | --- |
| `Memory` | Main memory manager |
| `MemoryEntry` | Stored record for one message or summary |
| `MemoryStore` | Store protocol |
| `InMemoryStore`, `SQLiteStore`, `FileStore` | Built-in stores |
| `SummarizeStrategy`, `SemanticStrategy` | Built-in memory strategies |

## What memory does

- stores new messages after a run
- retrieves prior messages for the same session
- applies a strategy when history grows too large

## Tested example

```python
import asyncio

from definable.memory import InMemoryStore, Memory
from definable.model.message import Message


async def main() -> None:
    async with Memory(store=InMemoryStore()) as memory:
        await memory.add(Message(role="user", content="My name is Ada."), session_id="docs")
        await memory.add(Message(role="assistant", content="Hello Ada."), session_id="docs")

        entries = await memory.get_entries("docs")

        assert len(entries) == 2
        assert entries[0].content == "My name is Ada."


asyncio.run(main())
```

## Choosing a store

- Use `InMemoryStore` for tests and ephemeral local runs.
- Use `SQLiteStore` when you want persistence without a separate service.
- Use `FileStore` when local file-backed persistence is enough.

Keep session IDs stable. Memory quality depends on good session scoping.
