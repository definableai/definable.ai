Definable exposes retry controls at more than one layer. The important distinction is scope:

- model retries wrap one provider call
- agent retries wrap one full run
- middleware retries wrap the execution segment they surround

## Tested retry middleware

```python
import asyncio

from definable.agent.middleware import RetryMiddleware
from definable.agent.run.agent import RunOutput
from definable.agent.run.base import RunContext

calls = {"count": 0}


async def flaky_handler(context: RunContext) -> RunOutput:
    calls["count"] += 1
    if calls["count"] < 3:
        raise ConnectionError("temporary")
    return RunOutput(content="ok")


middleware = RetryMiddleware(max_retries=2, backoff_base=0, backoff_max=0)
result = asyncio.run(middleware(RunContext(run_id="r1", session_id="s1"), flaky_handler))

assert result.content == "ok"
assert calls["count"] == 3
```

## What to configure where

- Model adapter fields such as `retries`, `delay_between_retries`, and `exponential_backoff` handle provider-level failures.
- `AgentConfig.retry_transient_errors` and `AgentConfig.max_retries` retry full runs.
- `RetryMiddleware` retries transient execution failures based on `ConnectionError`, `TimeoutError`, and `OSError`.

## Notes

- Tool exceptions are part of the normal control surface; the model can often recover if the error message is precise.
- Streaming failures surface through `RunError` events instead of through a completed `RunOutput`.
- Catch broad exceptions at the application boundary only after you decide which layer should own retries.
