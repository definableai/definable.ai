`Model` is the abstract provider adapter behind the agent loop. In day-to-day code you usually construct a concrete provider model such as `OpenAIChat` or resolve one from a string, but they all plug into the same base contract.

## Core fields

| Field | Meaning |
| --- | --- |
| `id` | provider model identifier such as `gpt-4o-mini` |
| `name` | optional local name for the adapter |
| `provider` | human-readable provider label |
| `context_window` | optional declared context-window size |
| `supports_native_structured_outputs` | provider can enforce schema natively |
| `supports_native_thinking` | provider supports native extended reasoning |
| `supports_json_schema_outputs` | provider expects JSON-schema response formatting |

## Common behavior

- Retry behavior lives on the model adapter through fields such as `retries`, `delay_between_retries`, and `exponential_backoff`.
- String shorthand resolution is handled by `resolve_model_string(...)`.
- The agent loop depends on the shared model contract, not on provider-specific branches in application code.

## Tested example

```python
from definable.model import OpenAIChat, resolve_model_string

direct = OpenAIChat(id="gpt-4o-mini")
resolved = resolve_model_string("openai/gpt-4o-mini")
defaulted = resolve_model_string("gpt-4o-mini")

assert direct.id == "gpt-4o-mini"
assert type(resolved).__name__ == "OpenAIChat"
assert defaulted.id == "gpt-4o-mini"

try:
    resolve_model_string("unknown/model")
except ValueError as exc:
    assert "Unknown model provider" in str(exc)
else:
    raise AssertionError("Unknown providers must raise ValueError")
```

## When to use strings vs provider classes

- Use a string when the model selection belongs in config or environment.
- Use a provider class when you need provider-specific features such as special headers, thinking settings, or compatibility options.
